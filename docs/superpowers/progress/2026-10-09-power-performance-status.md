# 省电与性能：真机状态盘点与压榨空间 — 2026-10-09

设备在本机（USB 直连）可用后的第一次省电侧盘点。所有数字来自设备自身经 `rf_logbuf`
上报的日志（`server/data/devicelogs/NOTE4C-3400FC.log`）、服务端 `schedule` 查询串里的
RTC 计数器（`w/a/r/g/f/er/eb/rr/c`），以及 UART0 抓的三次冷启动
（`/tmp/warm-capture.log`、`/tmp/clean-capture.log`、`/tmp/boot-capture.log`，均在 `/tmp`）。

> **观测前提（决定下面大半结论）**：设备**插着 USB**。`power.rs::decide()` 在 `mains` 上短路
> 返回 `StayAwake`（`firmware/main/rust/src/power.rs:54`），所以插电期间设备从不进深睡，
> 走不到深睡 teardown —— 而那正是 `awake_ms` / `radio_ms` 的记账点。**省电验收必须拔掉
> USB**，否则 `a=0&r=0` 不是回归。

## 1. 一条被误判的"回归"（先撤回）

服务端查询串在 10/8 16:53 之后一直是 `a=0&r=0`，看着像时长账本不再累积。**不成立**：

- 逐日统计 `a>0` 的批次数：09-25 = 123、09-29 = 113、09-30 = 141、10-02 = 143、10-08 = 62，
  **每一天都有非零批**（10/8 的 62 个非零批集中在 09:00–16:53，即插电之前）。
- 充电态与 `a>0` 的对应（10/8 抽样）：`a>0` 只出现在 `c=4`（电池），
  `c=2/c=3`（插电充电）时为 0。

**判据**：`a/r` 只在**电池供电且真的睡下去**的周期里累积。插电 + 反复 USB 复位刷写期间恒为 0
是设计使然。

## 3. 本次新查到的一个量化事实：快连缓存在深睡下工作正常

顺手核了 `wifi_station.cc` 的快连缓存（Stage 3，commit `e260846`），得到一个决定性对照：

| 唤醒类型 | `stage=wifi event=sta_connected t_ms` | 快连 |
|---|---|---|
| **真深睡唤醒**（设备日志，220 批） | **509 ms** | `event=fast_success` |
| **USB 复位唤醒**（UART0 抓包 ×3） | **4883 / 4911 / 4902 ms** | `reason=fail_threshold fail_count=0` |

⇒ 深睡唤醒走快连（0.5 s），USB 复位走全扫描（4.9 s），**每次唤醒差约 4.4 秒射频**。
这 4.4 s 不是回归，是复位类型的差异（`g_rtc_wifi_cache` 是 `RTC_DATA_ATTR`，USB/CPU
复位不清 RTC slow memory，但 RAM 侧的 `g_fast_cache` 已被清且 seed 早于首次 STA start）。

**顺带纠正一处日志误导**：`fast_direct_connect_skip reason=fail_threshold fail_count=0`
—— 实际条件是 `wifi_direct_allowed`/`wifi_scan_forced` 为真才落到 `else if (kFastRcEnable)`
分支，该标签把"策略要求扫描"说成了"失败次数超阈值"。日志文本误导，但不影响行为。

**`wrote=0` 的真义**（设备日志 222 次）：`SaveFastConnectCache` 返回 `changed`，yi02 的
`(ssid,bssid,channel)` 在 RAM 缓存里没变 ⇒ false；但 `SaveWifiCacheToRtc()` 在 `return`
之前已经执行 ⇒ RTC 镜像**照样写了**。`wrote` 是"RAM 是否变"，不是"是否持久化"。

   不值得为它改代码。
3. **EPD 刷新节流**：当前页时长（服务端 `duration`）驱动换页。若把静态页的时长调长，
   直接按比例削掉 `eb` 与 `er`。**但这是内容决策，不是固件优化**，且改动在服务端。
4. **`CONFIG_FREERTOS_USE_TICKLESS_IDLE` 未开**（`sdkconfig:3230`）⇒ light sleep 不可用
   （`main.cc:96` 已注明踩过 `ESP_ERR_NOT_SUPPORTED` 变 0.3 s 启动死循环的坑）。
   DFS-only 下 CPU 空闲仍跑 80 MHz。开 tickless 需要先解决 USB-Serial-JTAG 控制台
   被 light sleep 拆 pad 的问题（`main.cc:88-96` 的红线）——**风险高，收益仅限清醒窗口
   的 CPU 功耗**，而清醒窗口里 EPD 波形占 40 s/40.8 s，CPU 占空极低。**不推荐。**
5. **音频轨在刷屏前断电**（`rf_rails_audio(0)`，T2 引入）——**已核实为不可达，撤回**。
   静态部分成立：`rf_rails_audio` 全仓只有一处调用（关），`PowerAudioOn()` 只在开机
   `InitializePower()` 跑一次，`CheckAndUpdateAudioPowerState` 只管 codec 的 input/output。
   **可达性部分否证**：`Application::PlaySound` 无调用者，`TtsStreamer`/`AudioService::`
   在 `xiaozhi.elf` 里 **0 符号**（链接器已丢弃整条音频路径），且静默唤醒根本不初始化音频
   （`application.cc:494`）。⇒ 这版固件没有任何路径发声，**既不是 bug 也不耗电**。
   登记为「结构隐患」：等音频消费者接回来时，`rf_rails_audio(0)` 的单向性才会变成缺陷。

## §9 能耗测量：BQ27220 之类的板载方案能不能用

问题：除了 USB 功率计，有没有板载的能耗测量办法。结论如下（数据来自 TI 手册，芯片本身的
寄存器语义已逐条核对，不是印象）。

### 先确认板上现状（已核实）

- 本板**没有任何电量计/电流计**：全仓无 `INA2xx`/`BQ27`/`MAX17`/coulomb/fuel-gauge 引用，
  板级 `config.h` 无 `CURRENT`/`SHUNT`/`ISENSE`/`IBAT` 引脚。
- ESP32-S3 **片上无电量计**，IDF 也无任何功率/库仑测量 API。
- 唯一的电池测量是 `ReadBatterySampleForTelemetry()`，**只给 mV**（10 次 ADC 平均），
  充电方向靠 `CHARGE_DETECT_GPIO`/`CHARGE_FULL_GPIO` 两个 GPIO。与 `AGENTS.md` §7
  「无电流传感器、无燃料计」一致。
- **板载 I²C 已有三站**：RTC PCF8563 `0x51`、NFC `0x55`、ES8311（`I2C_NUM_0`）。

### BQ27220 能测什么（核到寄存器）

能。它是 CEDV 单节电量计，挂在电池与系统地之间测 10 mΩ 采样电阻压差，I²C 标准命令：

| 寄存器 | 地址 | 语义 |
|---|---|---|
| `AveragePower()` | 0x24/0x25 | **signed，单位 mW**；放电为负、充电为正 |
| `Current()` | 0x0C/0x0D | signed，mA |
| `RawCoulombCount()` | 0x22/0x23 | 库仑计数（放电累加、充电递减，充满清 0） |
| `RemainingCapacity()` / `FullChargeCapacity()` | 0x10 / 0x3C | mAh |
| `StateOfCharge()` | 0x2C | % |
| `TimeToEmpty()` | 0x16 | min |
| `StandbyCurrent()` | 0x1A | mA（芯片自身的静态电流口径） |

数据手册给的自身功耗：**NORMAL 50 µA / SLEEP 9 µA / SHUTDOWN 0.6 µA**。

### 三条否决理由（按严重度）

**① 采样电阻串在电池回路，芯片有规范盲区 —— 对本项目是致命的**
`Deadband` 出厂默认 **5 mA**，`CC Deadband` 默认 17×294 nV（≈5.6 mA）。手册定义：
**落在 ±Deadband 内的电流被报成 0 mA，且不计入库仑累加**（`Any current within ±Deadband ...
will be reported as 0 mA by the AverageCurrent() and is excluded from capacity accumulation`）。

本设备深睡电流落在 mA 级（1–10 mA），而唤醒峰值有几百 mA。后果：

- 库仑计在深睡期间**要么看不见、要么低计**，`RemainingCapacity()` 反而**不如现有的裸 mV 可信**；
- 而这个**深睡电流恰恰是本次省电优化要测的量**——刚改的唤醒节奏改的就是深睡占空比。

要测它就得把采样电阻换到 1 Ω 级（并重新校准/OTP 量产编程），那是改硬件设计，不是接线。

**② I²C 地址硬撞**：BQ27220 从地址**固定为 7-bit `1010101` = `0x55`**（可用仓库
`Xinyuan-LilyGO/T-Embed-CC1101/bq27xxx_test/bq27220_def.h` 复核：`BQ27220_I2C_ADDRESS 0x55`），
与本板 **NFC `0x55` 直接冲突**——接上去就是双设备抢地址。

**③ 工程量与不可逆性**：除芯片外还要串 10 mΩ 采样电阻、改电池走线、按实际电芯做 CEDV
参数标定（TI 的 GAUGEPARCal，或 OTP 量产编程）。这是**重做电池板**，不是加个测量点。

### 对照表

| 方案 | 能给出 | 代价 | 适用 |
|---|---|---|---|
| **USB 功率计** | 直接 mA/mW、mAh | 几块钱，串在 USB 与设备间 | **一次性回答"省了多少"** |
| **外部 INA219/INA226**（散件，串电池正极） | 板上长期 mA·h，可写进遥测 | ~¥10–20 + 焊接；本身就是电流表，无死区 | 想在设备端长期记录 |
| **BQ27220** | mW / mAh / SOC / TTE | 重做电池板 + 参数标定 + 解决 `0x55` 冲突 | **不适用**（见上三条） |
| **现有 `awake_ms`/`epd_busy_ms`** | 时长（负载代理） | 已到位 | 只能比"省了多少唤醒/刷屏"，**不能换成能量** |

### 结论

**要给"续航延长多久"的数字，仍然只有 USB 功率计一条最短路径。** BQ27220 解决不了本项目的
主要问题（深睡 mA 级电流恰在它的死区里），地址还与板上 NFC 冲突，且要重做电池板。
若确实想长期在设备端记录，**INA219/INA226 散件**比 BQ27220 更合适：无死区、无需化学参数
标定、I²C 地址可配（避开 `0x51`/`0x55`）。
