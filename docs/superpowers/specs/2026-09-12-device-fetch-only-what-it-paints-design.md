# 设备只取它要画的那一页（fetch only what it paints）设计

日期：2026-09-12
状态：待复核
提出：用户（「第一次拿到数据时同时拿到 md5 并保存起来，后续只比对、不自己计算」）

## 问题（已取证）

用户的模型是"服务端给的 md5 存起来，后续只比对"，并明确不自己计算哈希。设备**已经是这个模型** ✓：

- 设备从不计算任何哈希 ✓（`page_sync.rs` 全文件无 md5/sha 调用）；md5 只是不透明的 32 字符标识。
- 它保存服务端给的 md5：PSRAM 页面表 `Page{md5, bitmap}`（`page_sync.rs:73`）＋ 跨睡眠的 **48 字节 RTC 记录** `displayed_md5[33]` + index（`rust/include/shim_power.h:28`）。
- 三处比对：schedule 级（`:394`）、页级复用（`:415`）、屏上现状（`:565`+`:591`）。

**但有一处与描述不符，且代价真实** ✗：`sync_schedule` 的次序是「**先下载全部页的位图**（`:433` 循环）→ `all_ready`（`:442`）→ 提交 schedule md5（`:451`）→ **最后**才比对 RTC 决定要不要重绘（`:565` 之后）」。

后果：设备每轮唤醒都把**每一页**的位图重新拉一遍——已实测（服务端日志每次都是 `schedule updated: 2 pages, 2 downloaded`）。而"已下载集合"只存在于 PSRAM（`static TABLE`，`page_sync.rs:131`，非 `RTC_DATA_ATTR` ✗），深度睡眠醒来必然为空 ⇒ 复用循环（`:415`）永远匹配不到 ⇒ 每次唤醒 2×30 KB 的纯浪费（页数越多越糟）。

而设备醒着的窗口只有 8–16 s，页驻留 ≥10 min ⇒ **醒来期间不可能轮到下一页** ⇒ 预下载其它页在任何情况下都用不上 ✗。

## 目标

一次唤醒**至多下载一张位图**（要画的那一页），**屏上已经是它时一张都不下**。判断只用已有的 md5（schedule 的 + RTC 记录的），不新增持久化、不计算哈希。

## 非目标

- 不改哈希算法、不在设备上校验内容哈希（用户已明确"相信服务端" ✓）。
- 不新增任何持久化（NVS/RTC 记录都不扩）——RTC 记录已够用 ✓。
- 不改服务端、不改分页轮换语义（服务端仍权威决定 `current_index`）。
- 不改通知/弹层路径。

## 设计

### 1. 判定（全部发生在下载之前）

唤醒后：取 schedule（小 JSON，必须取，policy 与 index 都在里面）→ 解析出各页 md5 → 读 RTC 记录（校验 magic）→ 得到目标页 = `pages[current_index]`。

| 情形 | 动作 |
|---|---|
| RTC 记录有效 且 `displayed_md5 == 目标页 md5` | **下载 0 张、不重绘**，直接按 policy 重新入睡 ✓ |
| 记录无效（冷启动 / magic 不符 / 屏是空页提示） | 下载目标页 1 张 → 画 → 记录 → 入睡 |
| 记录有效但 md5 不同 | 下载目标页 1 张 → 画 → 重新记录 → 入睡 |
| 目标页位图下载失败 | 不重绘、不提交 ✓，下一轮唤醒重试 ✓ |
| schedule 为空（或该页缺字节被服务端跳过） | 走既有的空页提示路径（`EMPTY_PAGE`，`mark_pending(…, -1)`）✓ |
| schedule 本身取不到（服务端不可达/超时） | 行为不变：`sync_once` 返回 false、`LAST_SYNC_OK` 置假、按退避重新入睡，屏上保持原样 ✓（本次不改可达性策略） |

### 2. "提交"语义要改（这是本次唯一的结构性改动）

现在的契约是「**所有**位图都在 RAM 才提交 schedule md5」（`:451-452`，并有测试 `a_missing_bitmap_keeps_the_schedule_uncommitted_for_a_retry` 守着）。它存在的理由是"避免把缺失页永久跳过" ✓ —— 但一旦只取当前页，"所有位图都在 RAM"就永远不成立 ✗。

新的契约：**提交条件 = 本次要画的那一页取到了**（或确认屏上已经是它）✓。它保留原来的保护意图：只要真正需要的那张没到手，就不提交、下一轮重试 ✓；而不再要求那些本轮用不到的页也到场 ✓。

`have_schedule_md5` / schedule-md5 快路径（`:394`）随之退化为"省一次解析"——**保留**（无害，且不改动 commit 语义之外的逻辑 ✓），但它的语义注释要按新契约改写 ✓。

### 3. 只取当前页

`sync_schedule` 的下载循环从「遍历 `0..new_count`」改为「只处理目标页」✓。保留下载缓冲与 `download_bitmap` 不变 ✓；`Table` 仍按 md5 缓存（同一次唤醒内的重绘——例如通知弹层关闭后重画——仍可复用 ✓），只是不再为将来预取 ✓。

## 验收（都可在服务端观察，不需要读屏）

1. **每轮唤醒的位图请求数**：服务端日志里 `GET /api/pages/bitmap/…` 从「每轮 N 次」降到「≤1 次」，且**屏上未变的那一轮为 0 次** ✓。这条是主验收。
2. **设备侧串口**（短窗，一次一个读者）：出现 `show page i/N md5="…"` 的轮次与第 1 条里"下载 1 张"的轮次一一对应；其余轮次只有 schedule 请求 ✓。
3. **不回归**：通知弹层、空页提示、服务端 0 页、跨设备（每台各自轮换）、`degraded`（服务端不可达）路径行为不变 ✓。
4. **单元测试**（主机可跑，`cargo test`，沿用现有 fake shim 的宿主测试）：
   - 「RTC 记录显示屏上已是目标页 ⇒ 不调用下载、不 mark_pending」✓
   - 「记录过期 ⇒ 只下载目标页一次」✓（断言下载次数，而不是"下载了哪些"）
   - 「目标页下载失败 ⇒ 不提交、不画、下一轮可重试」✓（替换现有 `all_ready` 语义的那条测试）
   - 「schedule 为空 ⇒ 空页提示路径」✓（既有用例应保持通过）

## 风险

- **把"所有页都在 RAM"当契约的其他代码路径**：改动前必须 grep 所有 `all_ready` / `have_schedule_md5` / `TABLE` 的使用点，确认没有第三个消费者依赖旧语义 ✓（`:481` 附近还有一处注释提到"uncommitted schedule md5"，属同一契约 ✓）。
- **本轮只取一页是否够**：依据是"醒着的窗口 ≪ 页驻留" ✓。若将来服务端把驻留降到分钟级以下，这条不成立——在 spec 里记为**前提**，并在代码注释里写清 ✓。
- **RTC 记录的可信度**：magic + 越界 index 已有校验（`:565` 一带 ✓）；若记录说屏上是 X 而屏实际不是（例如上电后 EPD 掉了图），**现有行为也一样信任它** ✓ —— 本次不改此信任模型，只在验收里保留"空页提示/冷启动"两条路径不被破坏 ✓。
