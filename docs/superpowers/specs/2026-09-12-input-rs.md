# input.rs：按键路由移植到 Rust

**日期**：2026-09-12
**目标**：`firmware/main/rust/src/input.rs`（新增）、`application.cc` 的 9 个按键处理函数改为查表

## 为什么搬这个，而不是 `TransitionLifecycle`

`application.cc` 里有两层"状态机"：

1. **`TransitionLifecycle()`** —— 9 个状态（Boot/WifiConnecting/ApProvision/PairStart/PairWaitCode/SyncIdle/Sleep/Error），14 个调用点。它**不是决策**：每个调用点都是"做这件事的模块报告自己做完了"。没有守卫、没有事件→状态表、没有优先级。搬过去只会得到 setter + 名字表，还要给一条热路径加 FFI 跳转。**不做。**
2. **按键路由** —— 9 个处理函数，每个都是一串带守卫的优先级判断，决定"这一下由谁响应"：通知？画板？RawDraw UI？还是无动作。**这才是真状态机**，而且历史上真错过（技能里记着"按键被画板劫持"、"离开屏时用 `notify_dismiss_quiet` 而不是 `notify_dismiss`，否则画板会画回屏幕跟随后的切页抢屏"、"双击覆盖层在有通知/画板时会丢快照"）。

## 接口

```rust
pub enum Button { Up, Down, Boot }
pub enum Gesture { Click, DoubleClick, LongPress, ComboLongPress }

pub struct Inputs {
    pub button: Button,
    pub gesture: Gesture,
    pub notify_active: bool,       // 通知正在屏上
    pub canvas_displaying: bool,   // 画板当前画在屏上
    pub on_settings: bool,         // 当前页 == Settings
    pub previous_is_settings: bool,// 上一页 == Settings（"别切回自己"的守卫）
    pub config_mode: bool,         // 配网 AP 已起
    pub provisioning: bool,        // lifecycle == ApProvision
}

pub enum Action {
    Ignore,
    UiInput,                                   // 交给 RawDrawUiManager::HandleInput
    NotifyAck { agree: bool },
    NotifyDismiss,                             // BOOT 短按：彻底关闭（不发 ack）
    NotifyFetchNext,
    CanvasPrev, CanvasNext,
    CanvasStopDisplay,                         // 把屏交还 UI
    CanvasAllowDisplay,                        // 把屏交还画板
    EnterSettings { drop_orphan_notification: bool },
    LeaveSettings,                             // 回上一页 + 交还画板
    EnterWifiConfig,
    ExitWifiConfig { enter_settings: bool },   // 退 AP，按守卫决定是否进 Settings
    StopCanvas { enter_settings: bool },       // 交还屏，按守卫决定是否进 Settings
}
```

`drop_orphan_notification` 是策略（进 Settings 前要不要清掉孤儿弹窗），**"用 quiet 版清"是实现细节**——因为 `notify_dismiss()` 会把画板画回屏幕，与紧随的 `SwitchPage` 抢屏。这一条写在 C++ 的单一调用点注释里。

## 决策表（逐条对齐现有行为，不新增不删减）

| 按键 | 守卫顺序 |
|---|---|
| UP 短按 | `notify_active` → `NotifyAck{agree:true}`；`canvas_displaying` → `CanvasPrev`；否则 `UiInput` |
| DOWN 短按 | `notify_active` → `NotifyAck{agree:false}`；`canvas_displaying` → `CanvasNext`；否则 `UiInput` |
| BOOT 短按 | `notify_active` → `NotifyDismiss`；`canvas_displaying` → `NotifyFetchNext`；否则 `UiInput` |
| UP 双击 | `notify_active \|\| canvas_displaying` → `Ignore`；否则 `UiInput` |
| UP 长按 | `on_settings && !previous_is_settings` → `LeaveSettings`；否则 `Ignore` |
| DOWN 长按 | `provisioning` → `Ignore`；否则 `EnterSettings{drop_orphan_notification: notify_active}` |
| UP+DOWN 长按 | `EnterWifiConfig` |
| BOOT 长按 | `config_mode` → `ExitWifiConfig{enter_settings: !provisioning}`；`canvas_displaying` → `StopCanvas{enter_settings: !provisioning}`；否则 `UiInput` |

注：`StopCanvas` 即使处于配网也**先交还屏幕**（与现有代码一致：`page_sync_stop_display()` 在守卫之前），只是不再进 Settings。

## 验证

- **主机**：`cargo test`，约 20 个用例，每个对应一个可观察行为（"通知在屏时 UP 是同意"、"双击在有画板时无动作"、"配网时 DOWN 长按无动作"……）。
- **真机**：**按键无法程序化注入**，所以设备侧只能验证"改完之后设备仍正常启动、非按键路径不受影响、按键行为由你亲眼看"——这一点如实写在报告里，不假装验过。构建 + 主机测试 + 设备启动冒烟是本次的设备侧上限。
- 移植的判据是**逐条等价**：表格里每一格都能在旧代码里找到对应行。

## 执行结果（2026-09-12）

**主机**：`cargo test` **117 passed**（路由 26 + 边界契约 6，其余为既有模块）；`idf.py build` exit 0。

**哨兵证明**（都能失败）：
- 把 UP 短按的优先级倒过来（画板先于通知）→ `up_agrees_with_a_visible_notification` 失败（"按键被画板劫持"）
- FFI 映射忽略策略的 `switch_to_previous` → `the_c_side_is_told_when_leaving_settings_cannot_switch_pages` 失败

**改写过程中复核出的一处真实偏差（已修，测试先行）**：旧的 `OnUpLongPress` 在 Settings 页上**总会** `page_sync_allow_display()`——包括上一页也是 Settings、因此不切页的那一支。我的第一版表在那种情况返回 `Ignore`，把"交还屏幕"漏掉了。补了失败用例 → 改成 `LeaveSettings { switch_to_previous: bool }` → 通过。这是本次移植最实在的收获：一致的行为必须逐格对齐，不能凭直觉重写。

**真机**：按键**无法程序化注入**，所以设备侧只验到——刷入后 `Boot → WifiConnecting → WiFi connected → SyncIdle (paired, sync running)` → `schedule updated: 2 pages, 2 downloaded` → `show page 2/2` → `Stay awake (60000 ms)`，无错误。**按键行为本身未经设备验证**，需要人按（见交接清单）。
